## Coverage and limitations of the audit

The [question audit](../outputs/phase2/stage14b/v1_question_audit.csv) lists every original question, source links, candidate coverage and flags; the [pair audit](../outputs/phase2/stage14b/v1_pair_audit.csv) lists each pair, its source and checks. For all 241 original rows, automated comparisons found zero differences against the corpus passage, original extracted description/header text, pinned URL, source revision/path/hash fields, or retained raw-file SHA-256. This checks integrity, not truth, completeness, license validity, semantic relevance, or every possible ambiguity. Each question needs independent semantic review; automated flags are not an exhaustive fact-check. In particular, target identifiers, macro names, and source mentions are candidate-generation evidence only. Natural needs can have more than four relevant passages, but the initial pool is limited; header excerpts may omit enclosing `#if` conditions. Some source descriptions are terse, use replacement characters or require product/version context. Reviewer should check every excerpt against the linked full pinned source and mark uncertainty.

## Targeted source investigations

- **esp-08, ESP32-C6 DAC:** the complete [pinned C6 header](https://raw.githubusercontent.com/espressif/esp-idf/1c42e514c90ae621af33bde3b6ad3dac22edcbfd/components/soc/esp32c6/include/soc/soc_caps.h) has no `SOC_DAC_SUPPORTED` definition; this is not proof of absence. Espressif's [C6 temperature sensor documentation](https://docs.espressif.com/projects/esp-idf/en/latest/esp32c6/api-reference/peripherals/temp_sensor.html) describes a DAC within the temperature-sensor module, whereas its [DAC API documentation](https://docs.espressif.com/projects/arduino-esp32/en/latest/api/dac.html) lists general-purpose DAC channels for ESP32 and ESP32-S2. An internal converter and a user-accessible DAC peripheral are different interpretations. The draft question does not specify which; current target chunks do not explicitly resolve it. Ask the reviewer to clarify or replace the need and establish an eligible corpus passage; do not assign an absence label.
- **esp-11, ESP32-C61 RMT:** the entire [pinned C61 header](https://raw.githubusercontent.com/espressif/esp-idf/1c42e514c90ae621af33bde3b6ad3dac22edcbfd/components/soc/esp32c61/include/soc/soc_caps.h) contains no RMT support macro. Espressif's [C61 workshop description](https://developer.espressif.com/workshops/esp-idf-basic/lecture-1/) explicitly lists RMT for C61, while an [issue filed by a community user in Espressif's repository](https://github.com/espressif/esp-idf/issues/18239) says C61 lacks RMT. The latter is a user claim, not an official vendor ruling. The conflict and possible version/specificity differences need independent adjudication; neither the missing macro nor a generic migration guide settles it. No target passage explicitly answers the need.
- **esp-13, ESP32-C3 USB OTG:** the [pinned C3 header](https://raw.githubusercontent.com/espressif/esp-idf/1c42e514c90ae621af33bde3b6ad3dac22edcbfd/components/soc/esp32c3/include/soc/soc_caps.h) defines `SOC_USB_SERIAL_JTAG_SUPPORTED` but no OTG support macro. Espressif distinguishes the [fixed-function C3 USB Serial/JTAG controller](https://docs.espressif.com/projects/esp-idf/en/release-v4.3/esp32c3/api-guides/usb-serial-jtag-console.html) from USB OTG; its [peripheral comparison](https://docs.espressif.com/projects/esp-techpedia/en/latest/esp-friends/get-started/case-study/peripherals-examples/peripheral-description.html#usb-otg) explicitly lists chips with OTG and excludes C3. That is external evidence against C3 OTG, not an explicit negative in the frozen header chunks. Review whether this information need is answerable by any eligible corpus passage, or revise/exclude it under a documented policy. External web pages are linked, not silently incorporated into the corpus; their reuse rights have not been established.
- **cve-07:** the [pinned record](https://raw.githubusercontent.com/CVEProject/cvelistV5/f36061cc9d42937cd6a7a7321a89da7ef625a190/cves/2020/0xxx/CVE-2020-0688.json) describes Exchange memory corruption but does not name the control requested by the original question. The [NIST record](https://nvd.nist.gov/vuln/detail/cve-2020-0688) also includes a validation-key characterization in other metadata, so source scope and differing descriptions deserve review. V2 proposes a broader question; this does not establish that the pinned description resolves every characterization of the issue.
- **cve-01** asks for a component whereas the target passage names products; review specificity. **cve-15** and **cve-18** have terse target descriptions; review whether requested product context is present in the passage or only elsewhere in the record. No relevance decision has been made.

## Split-independence repair

The original `esp-01` (C2 core count), `esp-02` (C5 GPIO count), and `esp-03` (S2 UART count) mirror Phase 1 test information needs `test08`, `test07`, and `test10`, despite changing the chip. The original `natural-01`, `natural-02` and `natural-03` also ask generic core-count, GPIO-count, and UART-count questions corresponding to those same old test topics. Token overlap alone misses semantic matches. V2 proposes SHA-256, AES-256, HMAC and secure-boot dev needs instead, plus the broader `cve-07` wording. The [change log](../data/phase2/review_v2/change_log.json) records every original and replacement. These seven replacements were authored **after** inspecting source content and old question text, so their origin is source-conditioned, not question-first, and their appropriateness and cross-split independence still require human review. No old test results were consulted for these decisions.

The pinned [C2 source](https://raw.githubusercontent.com/espressif/esp-idf/1c42e514c90ae621af33bde3b6ad3dac22edcbfd/components/soc/esp32c2/include/soc/soc_caps.h) contains `SOC_SHA_SUPPORT_SHA256`; the [C5 source](https://raw.githubusercontent.com/espressif/esp-idf/1c42e514c90ae621af33bde3b6ad3dac22edcbfd/components/soc/esp32c5/include/soc/soc_caps.h) contains `SOC_AES_SUPPORT_AES_256`. Those records support candidate construction, not automatically positive judgments. The original pair IDs are retained with changed question text in v2; the v1 package is the authoritative historical mapping. New candidate IDs are never assigned to different old pairs.

This remains below the five-case target; no invented cases or external document additions were used.

The [confusable inventory](../outputs/phase2/stage14b/in_corpus_cve_confusables.json) applies character-level Levenshtein distance to full same-year CVE identifiers, comparing 36 needs with actual in-corpus CVE records. It finds 10 directed query–document cases at distance two and none at distance one; one was already in v1 and the nine others are added, unjudged, to v2. These string-near records are not necessarily semantically difficult, relevant, or independent. They do not establish a target quota or justify synthetic IDs.
